# 0001. Вход через Яндекс ID и аккаунт с ролью

Статус: **принято 9 октября 2026 года** (решение владельца: вход «в один клик через
соцсеть, например, Яндекс», после входа — онбординг-чат; демо-вход для жюри
остаётся). На стенде сдачи пока работает только демо-вход; вход через Яндекс
включается заданием `YANDEX_CLIENT_ID`/`YANDEX_CLIENT_SECRET`.

Требования: R-N-07 (ролевой доступ, защита от НСД, безопасное хранение токенов),
R-C-14 (согласие на обработку ПДн, 152-ФЗ), R-E-01…03 (нужен работодатель как
пользователь). **Расхождение:** R-D-04 требует «регистрацию по email с
подтверждением». Вход через Яндекс ID закрывает регистрацию, но не «по email с
подтверждением» — см. «Открытые вопросы».

## Вопрос

Как реализовать вход: свой OAuth-клиент Яндекс ID поверх существующей
подписанной cookie-сессии или Auth.js (NextAuth v5) с провайдером Yandex.

## Варианты

**(а) Свой authorization code flow + PKCE (выбрано).** `GET /api/auth/yandex` →
`oauth.yandex.ru/authorize` → `GET /api/auth/yandex/callback` → `POST
oauth.yandex.ru/token` → `GET login.yandex.ru/info`. Около 150 строк, без новых
зависимостей. Сессия — та же HMAC-кука `cid`, что у демо-входа.

**(б) Auth.js v5 + `next-auth/providers/yandex` + `@auth/prisma-adapter`.**
Готовый провайдер (сверено по докам Auth.js через Context7). Против:
- две новые зависимости и вторая система сессий рядом с `cid`, на которую уже
  опираются 11 роутов через `requireCandidate`;
- схема адаптера Prisma требует `User.email String @unique` (обязательный) и
  хранит `access_token`/`refresh_token` в `Account`; у нас почты от Яндекса может
  не быть, а токены Яндекса после входа не нужны — хранить их значит расширять
  поверхность утечки (R-N-07);
- демо-вход за готовых кандидатов пришлось бы встраивать как Credentials-провайдер
  или держать параллельно.

Весомой причины для (б) нет: нужен один провайдер и один сценарий.

## Решение

1. **Протокол** (доки Яндекс ID: yandex.ru/dev/id/doc/ru/codes/code-url,
   …/user-information). `response_type=code`, `state` (24 байта случайных),
   PKCE `S256` (verifier 48 байт → 64 символа base64url). `scope=login:info
   login:email`. Обмен: `client_id`, `client_secret`, `code_verifier` в теле
   `x-www-form-urlencoded`. Профиль: заголовок `Authorization: OAuth <token>`.
   `redirect_uri = ${APP_URL}/api/auth/yandex/callback`.
2. **state и verifier** — в короткоживущей подписанной куке `yoauth` (HMAC с
   отдельным контекстом, 10 минут, `HttpOnly`, `SameSite=Lax`, `Path=/api/auth/yandex`).
   Кука удаляется на любом исходе callback.
3. **Токен Яндекса не хранится**: живёт в памяти запроса до получения профиля.
   Токены и код не логируются; в лог идёт только стадия и код ошибки Яндекса.
4. **Модель.** Новый `User` (роль `pending | candidate | employer`, `name`,
   `email?`, `isDemo`, `onboardedAt?`, `candidateId? @unique`) + `AuthAccount`
   (`@@unique([provider, providerAccountId])`) + `EmployerProfile` (1–1 с User,
   ссылка на `Company`) + `Consent` (версия текста + время, записи не удаляются).
   `Candidate` не меняется (только обратная связь `user`): на нём держатся
   утверждения, загрузки, диалоги, приглашения — роль в Candidate потянула бы
   правку всех этих связей, а работодатель кандидатом не является.
5. **Роль выбирается в онбординге один раз** (`POST /api/auth/role`). До выбора —
   `pending`: доступен только онбординг. Кандидату создаётся `Candidate`
   (почта Яндекса, если она есть и не занята, иначе служебная
   `user-<id>@users.invalid` — `Candidate.email` обязателен и уникален).
   Работодателю — новая `Company` (`isDemo=false`); вступить в чужую компанию
   нельзя (верификации компаний в MVP нет, R-D-05).
6. **Аккаунты по почте не склеиваются**: ключ — только `provider +
   providerAccountId`. Иначе почта, совпавшая у другого способа входа, дала бы
   доступ к чужому аккаунту. Почты нет → `email = null`, онбординг может спросить.
7. **Сессия.** Кука `cid` двух форматов: старый `<candidateId>.<exp>.<sig>`
   (продолжает работать — экраны демо не ломаются) и
   `u.<userId>.<role>.<candidateId>.<employerProfileId>.<exp>.<sig>`. Роль и id
   профиля в подписанной куке, чтобы `requireCandidate` остался синхронным и
   без запроса в БД. Смена роли перевыпускает куку. `HttpOnly`, `SameSite=Lax`,
   `Secure` при `https` в `APP_URL`, 30 дней; значение меняется при каждом входе.
8. **Guard-ы.** `requireCandidate` (401/403), `requireEmployer`, `requireUser`
   (любой аккаунт, включая `pending`); для страниц — `requirePageUser`,
   `requirePageEmployer` (редирект на `/auth?next=…`).
9. **Редиректы.** После входа: онбординг не завершён → `/onboarding`; иначе
   `next` (только относительный путь сайта, не `/api/`, без `//` и `\`) или
   кабинет роли (`/consultant`, `/employer`).
10. **CSRF.** Все изменяющие запросы — POST; кука `SameSite=Lax`; если браузер
    прислал `Origin`, он должен совпадать с `APP_URL` или адресом запроса.
11. **Согласие (R-C-14).** `recordConsent(userId, version)` пишет факт, версию и
    время; принимается только текущая версия (`CONSENT_VERSION`, текст —
    [consent.md](../consent.md), черновик). Завершить онбординг без согласия на
    текущую версию нельзя.
12. **Демо.** Вход за демо-кандидата создаёт ему аккаунт при первом входе
    (роль `candidate`, онбординг пройден). Демо-работодатель — в сиде
    (`prisma/seed/auth.ts`, компания `demo-co-northstream`). Решение владельца
    09.10: демо-аккаунты не показываются на `/auth` (там только Яндекс ID), а живут
    на отдельной странице `/demo`. Страница и `/api/demo/login` работают только при
    `DEMO_LOGIN=true` (на стенде жюри включено, на проде выключить), иначе 404;
    тихая ссылка «Демо для жюри» — в подвале главной и на `/auth`, тоже только по флагу.

## Последствия

- Другие лейны проверяют доступ через `requireCandidate`/`requireEmployer`/`requireUser`
  и не читают куку сами.
- Сессия без хранения на сервере: принудительно отозвать вход до истечения
  30 дней нельзя (кроме смены `SESSION_SECRET`). Для хакатона приемлемо.
- Роль в куке может устареть, только если её сменить в БД вручную; штатная смена
  идёт через `/api/auth/role` и перевыпускает куку.

## Дополнение 10.10: email-регистрация

Решение владельца 10.10 (Q-34): R-D-04 «регистрация по электронной почте с
подтверждением адреса» закрываем буквально. Основной вход — почта + пароль с
подтверждением 6-значным кодом из письма; Яндекс ID остаётся дополнительным входом,
демо-вход — как был.

1. **Модель** (миграция `20261010053339_email_auth`, аддитивно). `User.passwordHash?`
   (scrypt из `node:crypto`, N=2^15, r=8, p=1, соль 16 байт, параметры в строке хэша),
   `User.emailVerifiedAt?`, таблица `AuthCode` (`purpose: verify | reset`, HMAC-SHA256
   хэш кода с ключом `SESSION_SECRET` и привязкой к назначению и пользователю, срок
   15 минут, до 5 попыток, `consumedAt`). Новый код гасит прежние того же назначения.
2. **Уникальность почты — через `AuthAccount(provider = "email", providerAccountId =
   почта в нижнем регистре)`**, а не `@unique` на `User.email`: у Яндекс-аккаунтов почта
   может совпадать, и п. 6 (аккаунты по почте не склеиваем) остаётся в силе — Яндекс-
   аккаунт и email-аккаунт с одной почтой — два разных аккаунта.
3. **Маршруты:** `POST /api/auth/register` (почта, пароль ≥ 8, версия согласия из галки —
   без неё аккаунт не создаётся), `/verify` (код → `emailVerifiedAt`, кука `cid`),
   `/verify/resend`, `/login`, `/password/forgot`, `/password/reset`. Все — Zod, CSRF по
   `Origin` (п. 10), `withErrors`. После входа — те же правила редиректа (п. 9): новый
   аккаунт `pending` → `/onboarding`, роль спрашивает онбординг-чат.
4. **Без перечисления аккаунтов:** неверная почта и неверный пароль — одинаковый 401
   `invalid_credentials` и одинаковое время (scrypt против хэша-пустышки); «забыли
   пароль» — всегда 200; повторная регистрация на подтверждённую почту — тот же ответ,
   пароль не меняется, владельцу ящика письмо «аккаунт уже есть». Неподтверждённую
   регистрацию можно повторить (иначе чужую почту можно было бы занять навсегда).
   Вход с верным паролем, но неподтверждённой почтой — 403 `email_not_verified` и новый код.
5. **Лимиты:** в памяти процесса (стенд — один экземпляр): письма на адрес 5 / 15 мин,
   вход на адрес 10 / 15 мин, ввод кода на адрес 20 / 15 мин, любые формы с одного
   клиента (`X-Forwarded-For` от Caddy) 60 / 15 мин; плюс 5 попыток на сам код в БД.
6. **Почта** — `src/server/mail/`: свой минимальный SMTP-клиент на `node:net`/`node:tls`
   (почтовой библиотеки в стеке нет), на стенде Mailpit; `MAIL_PROVIDER=log` — письма
   в лог и журнал в памяти (тесты). Ошибка SMTP при отправке кода: на демо-стенде не
   мешает (код на экране), иначе 503 `mail_unavailable`.
7. **Демо-стенд** (`DEMO_LOGIN=true`): код подтверждения возвращается в ответе и
   показывается на экране с пометкой «демо-стенд: письма идут в Mailpit» — жюри
   регистрируется без доступа к ящику. Код **сброса пароля** не показывается никогда:
   иначе любой посетитель стенда сменил бы чужой пароль.
8. **Уведомления:** письмо кандидату о новом приглашении (`createInvitation`) и
   работодателю-отправителю о принятии/отклонении (`respondInvitation`) — в фоне, без
   ожидания и без влияния на ответ; ошибка — в лог. Служебные адреса
   `*@users.invalid` пропускаются. В письме работодателю нет данных кандидата — они в
   кабинете по правилам раскрытия (R-E-07).

Последствия: смена пароля не отзывает уже выданные куки (сессия без хранения на
сервере, см. «Последствия» выше); лимиты сбрасываются при перезапуске и считаются
на каждую реплику отдельно.
