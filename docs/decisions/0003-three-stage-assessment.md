# ADR 0003. Три ступени оценки: созвон → проект под работодателя → защита

- Статус: принято 10.10.2026 (решения владельца продукта, виджеты 10.10); реализация – лейнами по
  плану ниже
- Основание: ресёрч владельца `research/24` (мировая практика: Karat, Codility, micro1; Lehtinen/QLC –
  вопросы по своему коду предсказывают успех лучше сданного кода; индустрия 2025–26 разрешает ИИ и
  проверяет понимание), инвентаризация кода 10.10
- Не отменяет ADR 0001 (профиль доказанности) и ADR 0002 (тест на грейд): **категорию задаёт тест**,
  ступени добавляют доказательства и картину для работодателя

## Решения

1. **Ступень 1 – квалифицирующий созвон** в том же чате кандидата (`/consultant`): кнопка
   «Созвониться» или предложение агента → правая панель переключается в режим звонка (аватар сверху,
   текст реплики ИИ снизу, микрофон, индикатор записи), лента чата сворачивается. ИИ задаёт 4–6
   зондирующих вопросов по специализации и резюме (маршрут по уровню: после ответа – уровень выше или
   ниже), **отдельный слепой оценщик** по рубрике A-02 (глубина / «почему так» / граница знаний /
   доведение, 0–2) ставит оценку по каждой затронутой теме. Результат – «карта глубины»
   (тема → заявлено → копнули → подтвердилось/нет) в профиле кандидата и в карточке работодателя.
   Категорию не меняет; утверждения, подтверждённые в созвоне, получают уровень `platform` (как защита).
2. **Ступень 2 – проект под работодателя.** Работодатель выбирает **базовый шаблон** платформы
   (спец × грейд; контракт + скрытые тесты фиксированы), задаёт **обязательные критерии** (из каталога
   утверждений) и **пожелания свободным текстом**; ИИ формирует условие проекта в домене работодателя и
   рубрику для LLM-проверки пожеланий. Кандидат получает проект по приглашению (или сам берёт открытый
   проект потребности), пушит репозиторий, указывает **журнал работы с ИИ** (ИИ разрешён явно).
   Автопроверка: скрытые тесты шаблона → балл (воспроизводим); статанализ; LLM-рубрика по критериям
   и пожеланиям → пояснения и флаги, **не балл**. Результат – таблица «критерий → прошёл/нет →
   доказательство» в отчёте работодателю. Детали шаблонов – после разведки Worker-билдера (отдельный
   раздел ниже, дополняется).
3. **Ступень 3 – защита проекта.** Ведёт ИИ голосом с аватаром (тот же режим звонка): вопросы
   генерируются из кода и коммитов кандидата (QLC), плюс «измени поведение»/«смени ограничение», плюс
   очередь вопросов работодателя. **Работодатель может подключиться живьём**: входит в комнату, может
   перебить, «замьютить ИИ» (ИИ не вступает, пока не разрешат) и говорить сам – аудио **WebRTC P2P**
   (сигналинг через наш API, публичный STUN), текст как запасной канал. Вопросы работодателя, заданные
   **после** защиты, копятся в очереди и задаются кандидату при следующем входе (асинхронная дозащита).
   Оценка – по рубрике A-02 отдельным оценщиком; **слабая защита при сильном проекте = флаг
   работодателю, не понижение**; автоматического вердикта «фейк» нет (ст. 16 152-ФЗ).
4. **Запись.** Транскрипт + аудио кандидата (файлы на диске, не в БД), отдельный пункт согласия перед
   первым звонком; работодатель видит запись только после принятого приглашения (R-C-16: до контакта –
   псевдоним). В подборке – только оценки по рубрике и флаги.
5. **LLM.** Локально – ключи владельца (`openai-chat`/DeepSeek и Yandex); если оценщику не хватает
   мощности – более сильная модель через российских провайдеров или локальная. Все новые вызовы – через
   `llm/client.ts` с новыми `LlmPurpose`, stub-провайдер возвращает детерминированные ответы.

## Контракты для параллельных лейнов (обязательны)

### Схема данных (`prisma/schema.prisma`, секции `// lane: <name>`; миграции собирает интегратор)

- `CallSession` (lane call): id, candidateId, kind `qualifying | defense`, projectSubmissionId?,
  status `active | finished | cancelled`, startedAt, finishedAt, transcriptJson (реплики с ролями
  `ai | candidate | employer`, таймкоды), audioPath?, verdictJson? (рубрика), policyVersion.
  `DefenseSession` остаётся для защиты утверждений; защита проекта – `CallSession.kind=defense`.
- `CallParticipant` (lane call): callSessionId, userId, role `employer`, joinedAt, leftAt,
  aiMuted bool.
- `EmployerQuestion` (lane call): id, companyId, candidateId, projectSubmissionId?, text, askedAt,
  answeredInCallSessionId?, status `queued | asked | answered`.
- `DepthMap` – не отдельная модель: результат ступени 1 хранится в `CallSession.verdictJson` и
  проецируется в `Claim.level=platform` для подтверждённых утверждений.
- `ProjectTemplate` (lane project): id, specialization, grade, title, contractMd, hiddenTestsRef
  (путь в `platform/project-templates/<id>/`), stackTags, visibleTestsRef.
- `ProjectTask` (lane project): id, vacancyId, templateId, specJson (сгенерированное условие),
  requiredCatalogIds[], wishesText, rubricJson, createdAt.
- `ProjectSubmission` (lane project): id, projectTaskId, candidateId, repoUrl, commitSha,
  aiLogText, status `submitted | running | checked | failed`, resultJson (тесты / статанализ /
  рубрика), submittedAt, checkedAt.
- `Consent` – новая версия с пунктом записи (lane call), константа версии в одном месте.

### API (все маршруты – в OpenAPI через `npx tsx scripts/build-openapi.ts`; zod-схемы в `src/server/*/schemas.ts`)

- lane call: `POST /api/call/start {kind, projectSubmissionId?}` → `{sessionId, webrtc: {iceServers}}`;
  `POST /api/call/{id}/turn {text | audioRef}` → реплика ИИ `{text, audioUrl?, done}`;
  `GET /api/call/{id}/events` (SSE: реплики, участники, mute, вопросы работодателя);
  `POST /api/call/{id}/finish`; `POST /api/call/{id}/signal {sdp|ice}` (сигналинг WebRTC);
  `POST /api/employer/call/{id}/join | /mute-ai | /say {text}`; `GET /api/call/{id}/recording`
  (кандидату – всегда, работодателю – после accepted-приглашения);
  `POST /api/employer/questions {candidateId, text}`; `GET /api/employer/questions?candidateId=`.
- lane runner: внутренний сервис `runner` (compose), HTTP `POST /run {repoTarballUrl | repoUrl,
  commitSha, testsBundleRef, image, timeoutSec}` → `{jobId}`; `GET /run/{jobId}` →
  `{status, tests: [{name, passed, ms}], lint: {...}, logTail, durationMs}`; без сети у задания,
  лимиты CPU/RAM/время/размер, один job за раз на машине; токен между app и runner
  (`RUNNER_TOKEN`). **Уточнено при реализации (10.10):** у runner нет интернета, поэтому tarball
  репозитория скачивает app (`submitRun` в `src/server/runner/client.ts`: GitHub tarball через SSRF-фильтр
  сборщика, ≤ 50 МБ) и передаёт его телом `POST /uploads` → `{uploadId}`; `repoTarballUrl` –
  `upload:<uploadId>`, `repoUrl` в `POST /run` отклоняется (422). Общий volume не выбран: права на
  томе между двумя uid и разный путь локально/в Docker. `lint` пока не заполняется; в ответе есть
  `reason` для `failed` и `summary`. Подробно – `platform/runner/README.md`.
- lane project: `POST /api/employer/needs/{id}/project` (создать/перегенерировать задание),
  `GET /api/project-tasks/{id}` (кандидату – условие, видимые тесты),
  `POST /api/project-tasks/{id}/submissions {repoUrl, aiLogText}`,
  `GET /api/project-submissions/{id}` (статус/результат), `GET /api/employer/project-submissions?needId=`.

### Точки стыка

- Ранжирование/карточка: `CandidateEvidence` получает `calls: {qualifying?: verdict, defense?:
  verdict}` и `projects: [{taskId, score, flags}]`; `scoreCandidate` учитывает проект под **эту**
  потребность (бонус, константа в `employer/weights.ts`), `Explanation` и `CandidateCard` показывают
  карту глубины, результат проекта, флаги защиты. Это делает lane employer-card **после** остальных.
- Уровень `platform` для утверждений – только через существующий путь (`claim.updateMany`, как в
  `test/service.ts:342` и `defense/session.ts`).
- Stub: `llm/providers/stub.ts` получает детерминированные ответы для новых purpose
  (`call_interviewer`, `call_evaluator`, `project_spec`, `project_rubric`, `defense_qlc`).
- UI: режим звонка – компонент `CallPanel` в правой панели `/consultant` (тот же аватар
  `components/avatar`, `/api/tts`, `/api/stt`), кнопка в `Composer`; работодатель – страница
  `/employer/calls/[id]` (комната) и блок «Вопросы кандидату» в карточке.

## Дополнение 10.10 (решения владельца, виджеты 15:00–15:30): лента заданий и четыре направления

6. **Выдача проекта – лента обезличенных заданий до приглашения.** Главная боль, которую решаем, –
   работодателя (тысячи откликов на вакансию, фермы и сгенерированные резюме; тезис владельца, источник
   для слайда ещё нужен). Работодатель публикует задание к потребности в категорию; кандидат

   задача для защиты), берёт не больше `PROJECT_MAX_ACTIVE = 3` одновременно, сдаёт репозиторий.

   открываются контакт, запись и комната защиты. Приглашение по-прежнему можно отправить и без
   задания. Общий мини-проект категории (вариант D) не делаем.

### Дополнение 10.10 (15:50 МСК): тест на грейд – отдельный на подкатегорию

8. **Категория = направление × подкатегория × грейд.** Решение владельца (виджет 15:45) после калибровки
   engineering: при общем тесте на направление узкий Junior одной подкатегории подтверждался в 60 %.
   Следствия (контракт для лейнов directions, engineering, generators-backend, generators-frontend):
   - `Candidate.subcategoryId` обязателен для старта теста (онбординг требует выбор); `TestAttempt`
     (и то, где хранится категория/результат) получает `subcategoryId`; `Vacancy.subcategoryId`
     обязателен для подборки по категории.
   - Политика выборки заданий (`test/policy.ts`, новая `POLICY_VERSION`): пул заданий – только семейства
     подкатегории кандидата; у каждого семейства генератора поле `subcategoryId`; минимум 8 семейств на
     подкатегорию (Junior и Middle по образцу a/b), иначе тест для подкатегории недоступен
     (`status=planned`), UI показывает «тест пока недоступен».
   - Персоны-калибровка – на подкатегорию (новичок, Junior, Middle, идеальный Junior), цель прежняя:
     новичок в Junior ≤ 10 %, Junior ≥ 90 %.
   - Подборка/фильтры: подкатегория – отдельный фильтр и часть объяснения; ранжирование внутри
     подкатегории, соседние подкатегории того же направления – ниже, с пометкой.
   - Сопоставимость R-T-02 – внутри подкатегории; это записать в документ сдачи.

### Дополнение 10.10 (16:15 МСК): пул заданий и грейд Senior

9. **Пул на подкатегорию: ≥6 Junior + ≥4 Middle + ≥4 Senior = 14 семейств** (решение владельца по
   калибровке gen-frontend: при 4 Junior «Junior с одной слабой темой» подтверждался в 50–75 %).
   `MIN_FAMILIES_PER_SUBCATEGORY` → 14 (или по грейдам: `{junior: 6, middle: 4, senior: 4}`).
10. **Грейд Senior.** `enum Grade` += `senior` (после middle). Политика (ADR 0002, новая
    `POLICY_VERSION`): `GRADE_CUT.senior` – предложение `+0.6` по θ (Middle −0.1, Junior −0.7),
    подтверждение тем же правилом `CONFIRM_PROB 0.8`; заявка Senior стартует с Senior-заданий, при
    P(θ>−0.1) в (0.2, 0.8) – дозадавание Middle (аналог `junior_probe`). Senior-задания: b от 1.0 до
    1.7, a 1.0–1.4 – проектные решения, компромиссы, диагностика по неполным данным, границы
    применимости. Калибровка персонами на подкатегорию: новичок, пограничный новичок, Junior,
    «Junior с одной слабой темой», Middle, «Middle с одной слабой темой», Senior, идеальный Junior;
    цели: ложное подтверждение ≤ 10 %, уверенный грейд ≥ 90 %, «с одной слабой темой» ≥ 85 %.
    Каталог утверждений: веса `S` уже есть (§ 7 каталога); `grades` записей – добавить `senior`,
    где уместно. UI/фильтры/ранжирование – три грейда везде, где перечислены два.
    Организаторам достаточно двух грейдов – Senior сверх ТЗ, в документе сдачи так и назвать.

    - ai.* – алгоритмы, структуры данных, SQL (выборки для обучения и аналитики), Linux (обучение и
      сервинг на серверах), тестирование (оценка и регрессии пайплайна);
    - engineering.* – Linux, Git, SQL, тестирование, HTTP (DevOps, SRE, QA, Data Eng работают
      в shell, с репозиторием, с данными и с HTTP-сервисами).
    Пул попытки `adr-0002-v7` = свои семейства + общие по карте (`poolFor(..., { common: true })`).
13. **Лимит доли: общих ≤ 30 % заданий попытки** (`MAX_COMMON_SHARE = 0.3`, policy.ts, ПРЕДЛОЖЕНИЕ).
    Правило префиксное: общее задание выдаётся, только если после него в каждом префиксе попытки общих
    не больше ⌊0,3 × длина⌋ – первое общее не раньше 4-го задания, при 10 заданиях не больше 3. Так
    лимит держится при любой длине (ранняя остановка, подтверждающий тест – тот же `selectNext`).
    В дозадавании Junior/Middle общих нет: оно уточняет грейд ниже по своей подкатегории. Исчерпание
    основной фазы считается по достижимому числу заданий (`reachableSize`). Симуляция (300 попыток на
    подкатегорию, θ ∈ [−2; 2], три грейда по кругу): средняя доля общих 0,15–0,22, максимум 0,30
    во всех 17 подкатегориях.
14. **Минимумы не размываются.** `bankComplete` и `MIN_FAMILIES_BY_GRADE` (6 J + 4 M + 4 S) считают
    только свои семейства: подкатегория без своего полного банка общими не «добирается».
15. **Совместимость.** Попытки `adr-0002-v6` и старше доигрываются по пулу из своих семейств; общие
    появляются только у новых попыток v7. Ротация (v5) учитывает общие семейства, виденные кандидатом
    в попытках любых подкатегорий. Шаблоны общих семейств заводит `ensureTemplates` (и сид) без ручных
    шагов; в `TaskTemplate.specialization` – «домашнее» направление семейства, пул ищет их по id.
16. **Длина основной фазы Senior – не больше 4 заданий** (`SENIOR_MAIN_MAX`). Раньше она шла до
    исчерпания Senior-пула (4 семейства); при ~8 Senior-семействах после расширения Senior с неверными
    Senior-ответами уходил в P(Middle) ≤ 0,2 и терял дозадавание Middle и «Middle в 1 клик». Больший
    Senior-пул работает на ротацию (randomesque из всех Senior-семейств). Junior и Middle от размера
    пула не зависят (7–10 заданий, дозадавание ≤ 3).
17. **Риск – размывание содержания: грейд подкатегории частично считается по общим темам.**
    Ограничен лимитом 30 %, отсутствием общих в дозадавании и тем, что полнота банка – только по своим
    семействам. Остаётся: a, b общих семейств – экспертные и одинаковые для всех подкатегорий (для
    фронтендера SQL может быть труднее, чем для бэкендера), на людях не калибровано. Каталог
    утверждений не имеет записей для Linux, регулярных выражений и конкурентности: эти семейства
    подтверждают `common.debugging` – запись в каталог стоит добавить отдельно.

### Дополнение 11.10: индекс честности теста в выдаче (решение владельца – вариант 2a + снятие созвоном)

Кандидат с индексом честности high (ADR 0002, § «Индекс честности и подтверждающий тест») опускается в подборке и в
поиске по банку: его категория из теста не учитывается ни в балле, ни в фильтре категории. В объяснении карточки так и
написано: «категория из теста не учитывается до подтверждения на созвоне». Понижение снимается в двух случаях:
категорию выдал подтверждающий тест (`confirmedAgain`) или квалифицирующий созвон / ИИнтервью разобрал задания именно
этой попытки и оценщик поставил «объяснил сам» (`testOwnership = explained`). Итоги `partial` и `failed`, а также
отсутствие созвона понижение не снимают. Созвон привязан к попытке так: это последняя завершённая до начала созвона
попытка, в которой есть все разобранные шаблоны заданий.

Метка у работодателя не меняется. Код: `src/server/employer/integrity-ranking.ts` (индекс грузится пакетно для всего
пула до ранжирования) и `ranking.ts` (`integrityPenalty: drop_category`). Выключатель – `TEST_INTEGRITY_RANKING`
(по умолчанию true).

Оценка: `docs/validation-results.md` § «Индекс честности в подборе, 11.10». Цену платит честный кандидат с ложным high:
без созвона он теряет место в фильтре своей категории всегда. Кандидату индекс не показывается, поэтому сам он на
созвон по этой причине не придёт. Доля пришедших и точность «объяснил сам» не измерены.
