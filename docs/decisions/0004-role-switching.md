# 0004. Переключение роли на одной учётке

Статус: **принято владельцем 10 октября 2026 года** (решение владельца по эпику E-05: «переключение
ролей нужно»). Пересматривает п. 5 ADR 0001 «роль выбирается один раз»; остальное в 0001 в силе.

Требования: R-N-07 (ролевой доступ, защита от НСД), R-C-14 (согласие на обработку ПДн), R-E-01
(профиль компании). Эпик — E-05 «две роли».

## Вопрос

Человек может быть и кандидатом, и работодателем (тимлид ищет работу и сам нанимает). Как дать ему
обе роли на одной учётке, не ослабив разграничение доступа: что значит `User.role`, где живёт второй
профиль, как проходит знакомство второй роли и что лежит в куке `cid`.

## Варианты

**(а) Активная роль + второй профиль на той же учётке (выбрано).** `User.role` — активная роль;
профили ролей уже раздельные (`Candidate` через `User.candidateId`, `EmployerProfile` 1–1 с `User`),
вторая роль — второй профиль. Переключение меняет `User.role` и перевыпускает куку.

**(б) Вторая учётка на ту же почту.** Не трогает модель, но ломает п. 6 ADR 0001 (аккаунты по почте не
склеиваем, а `AuthAccount(email)` уникален по почте) и заставляет выходить и входить заново: два
пароля, два согласия.

**(в) Обе роли сразу, без активной.** Гвард пускал бы по наличию профиля — работодатель с профилем
кандидата видел бы кабинет кандидата из кабинета работодателя, а интерфейс не знал бы, «из какой роли»
действует человек. Upwork и Airbnb держат явный активный режим ровно поэтому.

## Решение

1. **`User.role` — активная роль** учётки: с ней выпускается кука при входе. Роль `pending` остаётся
   состоянием «первая роль не выбрана» (страховка для старых аккаунтов; первую роль выбирает
   регистрация или знакомство, `POST /api/auth/role`, повтор — 409, как раньше).
2. **Вторая роль — второй профиль** на той же учётке, создаётся при первом переходе в транзакции:
   кандидату — `Candidate` (почта учётки, если не занята, иначе служебная; `consentAt` — из согласия
   учётки), работодателю — новая `Company` (`isDemo = false`) и `EmployerProfile`; вступить в чужую
   компанию по-прежнему нельзя (R-D-05). Профили не удаляются при переключении.
3. **Маршрут — отдельный `POST /api/auth/role/switch`**, а не расширение `/api/auth/role`: у того
   другой контракт (один раз, `pending → роль`, 409 на повтор, ответ с id профилей), у переключения —
   «роль → роль», идемпотентность и `next`. Смешать — значит ослабить проверку «роль уже выбрана»
   в знакомстве. Уровень `account` в `API_ACCESS`; `assertSameOrigin`, Zod, лимит 30 переключений на
   учётку за 15 минут (в памяти, как лимиты входа). Ответ — `{ role, next, created, changed }`.
   - профиль цели есть → переключить; нет → создать и запустить знакомство этой роли;
   - та же роль → 200, `changed: false`, ничего не меняется (кука перевыпускается);
   - старая демо-кука без `userId` → 403 «войдите заново на /demo»; без входа → 401;
   - `pending` → 409 «сначала выберите роль в знакомстве»;
   - работодатель без профиля и без `companyName` → 400;
   - **общий демо-аккаунт из сида** (`isDemo` без своего входа `demo`) → 403 при создании второй роли:
     им входят все члены жюри, и чужое «Стать работодателем» поменяло бы аккаунт всем. Для показа
     переключения — «Новый пользователь» на `/demo` (личный демо-аккаунт, у него вход `demo`).
   - Два одновременных перехода одной учётки (двойной клик, две вкладки) сериализуются блокировкой
     строки `User` (`SELECT … FOR UPDATE` в той же транзакции): профиль и компания создаются один раз.
4. **Знакомство второй роли — в ленте `/consultant`**, роль-специфичные шаги того же сценария
   (`scenarioSteps` по `facts.role`). Согласие дано учёткой — шаг согласия скрыт; название компании
   задаётся в переключателе — шаг `companyName` закрыт. Состояние знакомства у учётки одно
   (`OnboardingState`), ответы ролей не пересекаются, а текущий шаг, пауза «Настроить позже» и реплика
   итога (id шага `summary` общий для сценариев) — свои у каждой роли: при любом переходе они уходят в
   `meta.byRole[<прежняя роль>]` и достаются у целевой; новая роль начинает с первого шага
   (`swapRoleOnboarding`).
   `User.onboardedAt` значит «знакомство **активной** роли завершено»; роли с завершённым знакомством
   хранятся в `OnboardingState.meta.doneRoles` и пересчитываются при каждом переходе: уходя из роли,
   записываем, завершено ли её знакомство сейчас (сброс дебаг-панелью тоже учитывается), для целевой
   роли `onboardedAt` ставится, только если она в списке. Чистое решение — `planRoleSwitch`
   (`server/auth/role-plan.ts`), исполнение — `switchRole` (`role-switch.ts`).
5. **Кука несёт id профиля только активной роли.** Формат куки не меняется: `signUserSession` пишет оба
   id, `parseSession` отдаёт только id активной роли (так уже было после лейна `access`). Это защита в
   глубину: даже ошибка в гварде, который решил бы по наличию id, не даст данных неактивной роли.
   Гварды решают по `session.role` (`allowsLevel`), id профиля — второе условие. Места, решавшие по
   наличию id (дебаг-панель), переведены на `session.role`.
6. **После переключения — полная навигация на `next`** (`window.location.assign`), не
   `router.refresh()`: дом обеих ролей — один адрес `/consultant`, клиентское состояние ленты прежней
   роли должно сброситься, а корневой layout с шапкой при клиентской навигации не перерисовывается.
7. **Шапка** показывает активную роль («Кандидат» / «Работодатель · <компания>», для скринридера —
   префикс «Активная роль:») и переключатель: «Режим работодателя/кандидата», если второй профиль есть,
   иначе «Стать работодателем/кандидатом» с шагом подтверждения (профиль с ПДн одним кликом не создаём;
   работодателю — название компании). Escape и «Отмена» закрывают шаг и возвращают фокус
   (`shell/RoleSwitch`, данные — `roleMenuFor` в `SiteHeader`). Ролевые темы (`data-role`) — лейн `roleui`.
8. **Личные демо-аккаунты не публичны.** «Новый пользователь» с `/demo` — тоже `isDemo`, но со своим входом
   `demo`; после «Стать работодателем» в нём лежит профиль кандидата с ПДн. Список `/demo`, вход по
   `employerUserId`, «пройти заново» по `restartUserId` и дебаг-панель видят только общие сид-аккаунты
   (`SHARED_DEMO_USER`: `isDemo` без входа `demo`).
9. **Миграции нет.** Отметки и состояние знакомства ролей (`doneRoles`, `byRole`) — служебное поле JSON `OnboardingState.meta`, профили уже
   раздельные. Отдельный столбец (`User.onboardedRoles`) рассматривали и отказались: до сдачи меньше
   шагов деплоя, а `meta` уже хранит служебное состояние знакомства.

## Последствия

- Роль в куке должна совпадать с `User.role`: `sessionExists` сверяет её вместе с версией пароля.
  Переключение на одном устройстве делает куку другого устройства протухшей (страницы — через
  `/api/auth/stale` на вход, API — 401 `session_stale`); повторный вход выдаёт куку с текущей ролью.
  Иначе страница решала бы по куке, а онбординг и сервисы — по БД, и ответы писались бы в чужую роль.
- Удаление учётки (дебаг-панель) удаляет оба профиля: id берутся из БД, не из куки.
- Сброс знакомства (дебаг-панель, «пройти заново» на `/demo`) удаляет `OnboardingState` целиком — с ним
  `doneRoles` и `byRole`: после сброса знакомство неактивной роли при возврате к ней спросится заново.
- `/api/auth/me` по-прежнему описывает учётку из БД (оба id профиля, роль из БД), а не куку.

## Источники

- Next.js 15 (Context7, `/vercel/next.js`): куки меняются только в Route Handler или Server Action, в
  Server Component — только чтение; корневой layout не перерисовывается при клиентской навигации;
  `router.refresh()` перезапрашивает данные текущего адреса, не сбрасывая клиентское состояние.
- Prisma 6 (Context7, `/prisma/web`): интерактивная транзакция `$transaction(async (tx) => …)` с откатом
  по исключению; 1–1 через `@unique` на внешнем ключе; конфликты записи Prisma не повторяет сама.
- Блокировка строки `SELECT … FOR UPDATE` — поведение PostgreSQL (вывод, не сверено через Context7).
