# 0009. Админка: персонал отдельно от пользователей, вход с 2FA, журнал, матрица прав

Статус: **принято владельцем 11 октября 2026 года** (эпик E-08, решения в виджете ~18:30 МСК: отдельная
таблица персонала, три роли, ручная верификация компаний). Реализация фундамента — лейн `admin`.

Требования: R-N-07 (152-ФЗ, ролевой доступ, защита от НСД), R-D-05 и R-X-01 (верификация и защита от
недобросовестных работодателей — концепция), R-N-06 (OpenAPI), R-C-06 (категорию определяет только тест).

## Решения

1. **Персонал — отдельная таблица `StaffMember`, не значение `UserRole`.** ADR 0001 («одна учётка — одна
   роль: pending | candidate | employer») не меняется. Сотрудник не может войти в админку пользовательской
   учёткой и наоборот: у них разные таблицы, куки и гварды.
2. **Роли ровно три:** `owner` (всё, плюс персонал, настройки, метрики, выгрузки, журнал), `moderator`
   (очереди, компании, вакансии, приглашения, псевдонимы кандидатов; решает жалобы, флаги, апелляции,
   верификацию; блокирует компании, скрывает вакансии), `support` (карточки пользователей, ПДн через
   «Показать» с причиной; возражения, кулдауны, разблокировка входа, удаление по запросу субъекта).
   `analyst` нет. Матрица — одна таблица `server/admin/permissions.ts`, тест на каждую пару «роль × действие».
3. **Вход** `/admin/login`: почта + пароль (scrypt из `server/auth/password.ts`) → промежуточная кука
   `fsp_admin_pre` (5 минут, path `/api/admin/auth`, привязана к версии пароля) → код TOTP. **TOTP
   обязателен для всех ролей**: при первом входе выдаётся секрет и otpauth-URI, первый верный код включает
   2FA. TOTP — RFC 6238 на `node:crypto` (HMAC-SHA1, 30 с, 6 цифр, окно ±1 шаг), без новых зависимостей;
   повтор кода того же шага отклоняется (`totpLastStep`). Секрет в БД зашифрован AES-256-GCM ключом из
   `SESSION_SECRET`. Публичной регистрации нет: первого `owner` заводит CLI `scripts/admin-create.ts` на
   сервере (пароль из stdin/env, не из аргументов); остальных — owner в `/admin/staff`.
4. **Кука** `fsp_admin` = `a.<adminSessionId>.<exp>.<sig>`, HMAC-SHA256 с доменом подписи `admin:` —
   отличается от `cid` (без домена) и `fsp_expert` (`expert:`), так что ни одна из них не подставляется вместо
   другой. HttpOnly, SameSite=Strict, Secure на https, path `/`, срок 12 часов. Id в куке — строка
   `AdminSession`: выход, смена роли, отключение, сброс 2FA и смена пароля отзывают сессии сразу.
   Каждый запрос сверяет сессию и сотрудника (не отключён, 2FA включена).
5. **Гварды:** `requireStaff(req, action)` в каждом обработчике `/api/admin/*` (401 без сессии персонала,
   403 без права, CSRF-проверка Origin для мутаций), `requirePageStaff(path, action)` в каждой странице
   `/admin/*`. Таблицы `PAGE_ACCESS`/`API_ACCESS` админку не описывают — тест полноты матрицы доступа
   требует эти гварды для всех маршрутов под префиксами, открыты только шаги входа. Middleware ролей не
   проверяет (как решено в E-05), пароль стенда действует и на админку.
6. **Журнал `AdminAuditLog`** (кто, что, над кем, причина, до/после, ip, когда) — только INSERT: в коде нет
   update/delete, в БД триггер запрещает UPDATE и DELETE. Пишется в той же транзакции, что и действие.
   Решения модерации, блокировки, раскрытие ПДн и изменения персонала требуют причины.
7. **ПДн скрыты по умолчанию:** раскрытие — только `revealPii` (право `reveal_pii`, причина, строка журнала
   до чтения данных).
8. **Категорию и грейд админ не ставит** (R-C-06): в каталоге прав такого действия нет. Можно сбросить
   кулдаун, аннулировать попытку с объяснением, назначить пересмотр. Входа под пользователем нет.
9. **Верификация компаний — ручная модератором** (выписка ЕГРЮЛ или домен корпоративной почты), без API ФНС.

## Последствия

- Схема всех фаз E-08 заведена одной миграцией `20261011230000_admin_foundation`; лейны фаз пишут в
  свои поля (карта — `docs/admin.md`).
- Смена `SESSION_SECRET` делает секреты TOTP нечитаемыми: владелец сбрасывает 2FA
  (`/admin/staff` или `admin-create.ts --reset-totp`), сотрудник настраивает заново.
- Лимиты входа — в памяти процесса (`rate-limit.ts`), как у пользовательского входа: на стенде один экземпляр.
- Не сделано в фазе 0: IP-allowlist (`ADMIN_IP_ALLOWLIST`) и отдельный поддомен через Caddy — желательны
  перед боевой эксплуатацией.
