# Интеграция ФСП: API, данные и вход

## Что предусматривает ТЗ

[Подробное ТЗ](sources/originals/fsp-specification.pdf), разделы 2, 3.5 и 4:

> Ни API, ни описание структуры данных ФСП не предоставляются намеренно.

Команда сама определяет полезные сведения о достижениях, структуру хранения и отображение. Доступ к реестру, готовые данные кандидатов и вакансий, эталонная разметка и инфраструктура не предоставляются. Собственные тестовые данные могут быть синтетическими.

В отношении Keycloak ТЗ говорит:

> это ориентир, а не требование: команда вправе выбрать свой способ авторизации

Обязательны регистрация по email с подтверждением адреса, возможность связи профиля с ФСП ID и полноценная работа кандидата без истории ФСП. В сдаче нужна схема предполагаемой интеграции. Описание собственного API выполняется через OpenAPI.

## Что существует у ФСП

На 5 октября 2026 года [кабинет спортсмена](https://lk.fsp-russia.ru/login) уже предлагает вход через ФСП ID. Поэтому утверждение «ФСП ID пока вообще нет» некорректно. Однако наличие входа в кабинет не предоставляет нашему приложению доступ к авторизации или реестру.

ТЗ описывает Keycloak как основу будущей интеграции. Адреса подключения, регистрация приложения, разрешения и контракт данных для нашей команды в материалах не выданы. Прототип должен работать без них.

## Разделение ответственности

| Компонент | Назначение | Решение для хакатона |
| --- | --- | --- |
| Авторизация | Кто вошёл, какие у него права | Готовая библиотека авторизации либо собственный развёрнутый Keycloak |
| Связь с ФСП ID | Какой участник ФСП соответствует локальному пользователю | Предусмотреть отдельную связь; демонстрационные привязки явно помечать |
| Источник достижений | События, участие, результаты и спортивные разряды | Собственный адаптер с синтетическими данными |
| Категоризация и подбор | Подтверждение профессиональных навыков и рекомендации | Собственная бизнес-логика, тесты и валидация |

Keycloak предоставляет вход и токены через OpenID Connect. Стандартный ответ о пользователе не определяет перечень его спортивных достижений: состав дополнительных полей и доступ к данным согласуются отдельно. [Документация Keycloak](https://www.keycloak.org/securing-apps/oidc-layers).

## Предложение для реализации

1. Выбрать готовый механизм регистрации и подтверждения email. Разрабатывать собственную систему идентификации с нуля не требуется.
2. Отделить источник достижений интерфейсом `AchievementProvider`. Первой реализацией сделать `DemoAchievementProvider` с фиксированными синтетическими записями; отдельный HTTP-сервис для этого необязателен.
3. Сохранять локальный идентификатор пользователя независимо от внешнего. Будущий OIDC-вход и связь с участником не должны требовать смены всех идентификаторов приложения.
4. Отделить состояние «ФСП не привязан», «нет достижений» и «источник временно недоступен». Отсутствие ответа источника не равно пустой истории.
5. При появлении контракта ФСП добавить реальный адаптер и процедуру безопасной привязки аккаунта.

Собственный Keycloak полезен, если команда хочет показать работу с OIDC уже в демо. Он остаётся нашим сервером входа и не даёт доступа к данным ФСП. Для будущего подключения потребуются согласованные issuer, client ID, redirect URI, разрешения и способ идентификации участника; для конфиденциального клиента – также учётные данные приложения. Совпадения email или ФИО недостаточно для автоматического присвоения чужой спортивной истории.

## Предлагаемый состав достижения

`event_id`, название, дисциплина, дата, этап и уровень соревнования; индивидуальное или командное участие; команда; место и баллы; критерии с версией регламента; ссылка на источник; время получения и признак демоданных.

Личная роль, ссылка на проект и использованный стек – отдельные поля со своим происхождением. Если их сообщил кандидат, не помечать их подтверждёнными ФСП. Это предложение нашего контракта, а не описание существующего API организатора.

## Симулятор ФСП ID и реестра (10 октября)

Чтобы показать схему интеграции живьём, команда подняла **отдельный симулятор** в каталоге
[`fsp-sim/`](../fsp-sim/README.md): Keycloak 26 с реалмом `fsp-id` (пользователи-спортсмены с claim `fsp_id`,
клиент платформы `fsp-career` с PKCE и `client_credentials`, демо-партнёр) и API реестра на синтетических
данных (120 вымышленных спортсменов, 70 соревнований, 1035 записей о достижениях, разряды, протоколы,
согласия спортсмена на передачу данных партнёру). Адрес: https://fsp-russia2.ru (стартовая страница,
`/docs`, OIDC discovery `/auth/realms/fsp-id/.well-known/openid-configuration`).

Это реализация предложений выше, а не интеграция с ФСП: контракт, issuer и данные вымышленные, каждый
ответ помечен `X-FSP-Simulator: true`. Платформа `platform/` подключается к симулятору, когда заданы
`FSP_OIDC_ISSUER`, `FSP_OIDC_CLIENT_SECRET` и `FSP_API_URL` (`platform/src/server/fsp-id/`): вход и привязка ФСП ID
идут по OpenID Connect, достижения читаются из реестра токеном участника (`GET /api/v1/me/achievements`) в момент
входа или привязки. Без этих переменных платформа использует встроенный мок ФСП ID и демо-реестр
`collector/fsp-demo.ts`. Что из схемы подключения сделано, а что нет – в README симулятора.

Стартовая страница симулятора написана для жюри. На ней кнопки выполняют настоящие запросы к API и показывают
ответы, а реестр можно править руками: завести или удалить участника, внести ему достижение или разряд. Участником,
созданным на странице, можно войти через ФСП ID на платформе и увидеть внесённые записи в профиле – так
проверяется, что платформа читает реестр, а не показывает заготовленный пример. Правка открыта без входа; в
настоящем реестре записи вносит федерация, и таких маршрутов там быть не может.

## Что уточнить у экспертов

Уточнения о ФСП ID, способе получения достижений и составе записи ведутся в [едином списке вопросов](questions-for-organizers.md), Q23–Q27. Они не блокируют реализацию: условия ТЗ разрешают самостоятельную модель и тестовые данные.
