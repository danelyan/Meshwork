# Валидация ступеней 1 и 3: созвон и защита проекта

Актуальность: **10 октября 2026, 16:40 МСК**. Ступени — по [ADR 0003](decisions/0003-three-stage-assessment.md):
1 — квалифицирующий созвон (`platform/src/server/call`), 3 — защита проекта (`platform/src/server/defense-room`).
Модель — DeepSeek V4 Flash через Yandex AI Studio (`.env`, `LLM_PROVIDER=openai-chat`).

## Главное и оговорки

1. **Кандидаты — симуляция.** Каждую персону играет та же модель (LLM-актёр с заданным профилем знаний:
   `platform/eval/stages/runtime.ts`). Это не люди: актёр местами знает больше легенды (новичок и
   «чужое резюме» иногда дают учебно-правильный ответ про DLQ или уникальный индекс). Оценщик видит
   ответы того же семейства моделей, которое их написало, — это может завышать согласие.
2. **n маленький:** 4 персоны × 3 созвона (36 оценок тем) и 3 персоны × 3 защиты. Проценты ниже — счёт
   по этим прогонам, а не оценка точности на людях.
3. **Ступень 1 различает ожидаемое в 35 из 36 тем** (порог рубрики A-02 ≥ 5 из 8, «почему» ≥ 1, не больше
   одного нуля). Единственная ошибка — сильная тема Middle (`be.idempotency`), не подтверждённая в 1 из 3
   созвонов (сумма 3 против 5 в двух других).
4. **Ступень 3 отделяет «сделал сам» от остальных полностью** (6/6/6 против 3–4), флаг
   `strong_project_weak_defense` при проекте 0,95 сработал у (b) и (c) во всех 6 защитах и ни разу у (a).
   **(b) «ИИ целиком» и (c) «понимает частично» оценщик не различает** (средние 4,0 и 3,7): у защиты один
   балл на весь транскрипт, частичное понимание в нём растворяется.
5. **Запас до порога мал.** У ступени 1 ложные темы набирают до 4, верные — от 5; у ступени 3 (a) — 6
   при пороге 5. Один прогон оценщика меняет решение по теме в 22–33 % тем у (a) и (d); медиана трёх
   прогонов это сглаживает (между созвонами решение совпало в 100 % тем у (a), (b), (c) и 67 % у (d)).
6. **Четвёртая заявленная тема в созвоне не спрашивается никогда.** 4–6 вопросов при «не больше двух на
   тему» покрывают 3 темы; порядок тем детерминирован (вес, затем id), поэтому одна и та же тема выпадает
   во всех трёх созвонах (`be.sql-schema` у (a), `be.transactions` у (d)). Покрытие — 75 %.
7. **Найдена и исправлена несостыковка контрактов** (коммит в лейне validation): lane project пишет
   `resultJson.tests` как сводку `{passed, total, score}`, а defense-room читал `tests` только списком. С
   реальным сабмитом защита получала `projectScore = null`, флаг `no_project_result` и **никогда** не
   поднимала `strong_project_weak_defense`. Цифры ступени 3 ниже — после исправления.

## Процедура

```bash
cd platform
uptime                                   # load average < 12; вызовы LLM строго последовательные
npm run eval:call                        # ступень 1: 4 персоны × 3 созвона, живая модель из .env
npm run eval:defense                     # ступень 3: 3 персоны × 3 защиты
npm run eval:call -- --stub              # детерминированно, без ключей (проверка конвейера)
npx vitest run tests/unit/eval/stage-metrics.test.ts   # разбор метрик
```

Скрипты пишут в отдельную БД (`EVAL_DATABASE_URL` или `DATABASE_URL` с `validation`/`eval`/`test` в
имени — иначе отказ) и создают на каждый созвон и защиту нового кандидата с согласием на запись. Сессии
идут через сервисный слой (`startCall`/`submitTurn`/`finishCall`, `startDefenseRoom`/`candidateTurn`/
`finishDefenseRoom`), не через HTTP. Сырые результаты: `platform/eval/results/stages/{call,defense}-live.json`
(наблюдения по каждому созвону, баллы каждого прогона оценщика, расход вызовов и токенов).

**Ступень 1.** Каждой персоне заданы утверждения профиля (`self_reported`, из «резюме») и ожидание по каждой
теме: должна подтвердиться или нет. Интервьюер выбирает темы и уровень вопроса сам, оценщик — слепой,
3 прогона, медиана по признакам (`call/evaluator.ts`).

**Ступень 3.** Три маленьких Node-репозитория — `platform/tests/fixtures/defense/` (снимок вместо GitHub).
Сабмит «сильный»: `resultJson` в формате lane project, `tests.score = 0,95` (19 из 20 скрытых тестов).
Вопросы QLC генерирует модель по коду фикстуры (во всех 9 защитах — `generator: llm`), оценщик — тот же
`defense/evaluator.ts`, 3 прогона, медиана.

## Рекомендации по порогам и механике

1. **Порог ступени 1 оставить 5.** Ниже — ложные подтверждения у «чужого резюме» (9 из 21 тем при ≥ 4),
   выше — теряются верные темы (10 из 15 при ≥ 6).
2. **Расхождение прогонов показывать, а не решать:** тема, где три прогона оценщика разошлись в решении
   порога, — «нужен ещё один вопрос» в карте глубины, а не ✓/✗. На этих данных это 6 из 36 тем, и среди
   них единственная ошибка ((d) `be.idempotency`, прогоны 4/3/5). Полоса «медиана 4–5» слишком широкая —
   13 из 36 тем.
3. **Покрытие тем:** чередовать порядок тем между созвонами или поднимать в начало ещё не спрошенные
   платформой; иначе одна заявленная тема не проверяется никогда. Неспрошенные темы показывать в карте
   глубины как «не проверено».
4. **Защита — балл по вопросу (или по файлу), а не один на весь транскрипт**, как карта глубины у
   созвона: тогда (c) покажет «подпись понимает, очередь — нет», а не 4 из 8 наравне с (b).
5. **Флаг `strong_project_weak_defense` при `strongProjectScore = 0,8` оставить:** на этом наборе он
   разделяет полностью. Запас (a) над порогом — 1 балл; при `evaluator_disagreement` показывать флаг с
   пометкой «оценщик разошёлся».
6. **Следующий замер:** живые люди (хотя бы 3–5 человек команды и знакомых) по тем же сценариям;
   перекрёстный прогон персон по репозиториям; второй оценщик — другая модель.
