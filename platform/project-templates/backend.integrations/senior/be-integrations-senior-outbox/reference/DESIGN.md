# Outbox вебхуков: проектные решения

## Решения
События одного ключа (например, заказа) уходят строго по порядку: получатель видит «создан» раньше
«оплачен». Временные ошибки повторяются с экспоненциальной задержкой и потолком, 429 уважает
Retry-After партнёра. Предохранитель останавливает отправки, когда партнёр лежит, и пробует одним
запросом после паузы, чтобы не добивать его волной ретраев.

## Компромиссы
Порядок по ключу даёт head-of-line blocking: одно «застрявшее» событие держит все следующие события
ключа до исчерпания попыток. Это сознательная цена за порядок; dead letter освобождает очередь.
Предохранитель общий на партнёра: сбой из-за одного ключа тормозит всех – зато не спамим лежащий сервис.

## Границы применимости
Очередь в памяти: при рестарте процесса неотправленные события теряются – в бою outbox пишется в ту же
транзакцию БД, что и бизнес-изменение, а отправщик читает таблицу. Доставка «как минимум один раз»:
таймаут после успешной обработки даст повтор, поэтому получатель обязан дедуплицировать по id события.
При нескольких экземплярах отправщика нужна блокировка строк (SELECT … FOR UPDATE SKIP LOCKED) по ключу.
