# Контракт: оркестратор поэтапной выкатки (engineering.devops, senior)

Модуль `rollout.py` в корне репозитория. Python 3.12, только стандартная библиотека, без сети, без потоков и
реального времени: парк хостов и часы **подставляются** вызывающим кодом (тесты дают фейки).

```python
class RolloutError(ValueError):
    code: str   # "invalid_hosts" | "invalid_target" | "invalid_batches" | "invalid_health" | "journal_mismatch"

def plan_batches(hosts: list[str], sizes: list[int]) -> list[list[str]]
def rollout(hosts, target, fleet, clock, batch_sizes=(1,), health=None, journal=None) -> dict
```

## Интерфейсы, которые даёт вызывающий код

```python
fleet.version(host) -> str | None   # текущая версия; None — на хосте ничего не выкачено
fleet.deploy(host, version) -> None # ставит версию; может бросить любое Exception
fleet.remove(host) -> None          # убирает выкатку; может бросить Exception
fleet.healthy(host) -> bool         # здоров ли хост; исключение Exception считается «нездоров»
clock.now() -> число                # виртуальное время, секунды
clock.sleep(seconds) -> None        # продвигает виртуальное время
```

Исключения, не наследующие `Exception` (например, `KeyboardInterrupt` или своё `BaseException`), оркестратор не
перехватывает: они вылетают из `rollout` как есть (так тесты моделируют обрыв процесса).

## `plan_batches(hosts, sizes)`

Режет `hosts` по порядку на батчи: размер i-го батча — `sizes[i]`, а когда `sizes` кончились, повторяется последний
размер; последний батч может быть короче. Пример: 7 хостов, `sizes=[1, 2, 4]` → батчи по 1, 2, 4 хоста.
Валидация: `hosts` — непустой список непустых строк без повторов, иначе `RolloutError("invalid_hosts")`;
`sizes` — непустой список целых ≥ 1 (не `bool`), иначе `RolloutError("invalid_batches")`.

## `rollout(...)`

Проверки до любого вызова `fleet`/`clock`, в порядке: `hosts` (`invalid_hosts`), `target` — непустая строка
(`invalid_target`), `batch_sizes` (`invalid_batches`), `health` (`invalid_health`).

`health` — словарь `{"checks": int ≥ 1, "interval": число > 0, "timeout": число ≥ interval}`, по умолчанию
`{"checks": 2, "interval": 5, "timeout": 30}`; ключи можно указывать частично (остальные по умолчанию).

### Журнал (`journal`)

`journal` — обычный `dict`, который `rollout` **изменяет** по ходу работы (вызывающий код может сохранить его
в файл). Если передан `None`, используется новый пустой. Поля:

```python
{"target": str, "previous": {host: str | None}, "verified": [индексы батчей]}
```

`previous[host]` — версия хоста **до** выкатки (`None`, если ничего не было). Запись для хоста появляется
**до** первого вызова `deploy` для него (порядок записей = порядок начала выкатки). `verified` пополняется индексом
батча сразу после того, как батч прошёл проверку здоровья. Непустой журнал с другим `target` →
`RolloutError("journal_mismatch")`. Пустой журнал (`{}`) заполняется сам.

### Ход выкатки

Батчи строятся `plan_batches(hosts, batch_sizes)` по **всем** хостам (включая уже стоящие на целевой версии).
Батчи идут строго по очереди. Батч с индексом из `journal["verified"]` пропускается целиком — без единого вызова
`fleet`. Для остальных:

1. Для каждого хоста батча по порядку: если `fleet.version(host) == target` — пропустить (идемпотентность);
   иначе записать `previous[host] = fleet.version(host)` (если записи ещё нет — существующая запись не
   перезаписывается) и вызвать `fleet.deploy(host, target)`. Исключение `Exception` — сбой батча, причина
   `"deploy_error"`, `failed_host` = этот хост, остальные хосты батча не трогаются.
2. Проверка здоровья батча: `t0 = clock.now()`; цикл: `clock.sleep(interval)`, затем опрос `fleet.healthy(h)` для
   **каждого** хоста батча по порядку (без короткого замыкания). Если здоровы все — счётчик подряд идущих успешных
   раундов растёт на 1, иначе сбрасывается в 0. Счётчик достиг `checks` — батч принят, индекс добавляется в
   `journal["verified"]`. Иначе, если `clock.now() - t0 >= timeout`, — сбой, причина `"unhealthy"`, `failed_host` =
   первый нездоровый хост последнего раунда (если в последнем раунде все здоровы, а счётчик не набрался, — первый хост батча). Иначе следующий раунд.
   Проверка выполняется и для батча, где все хосты уже на целевой версии (но он не в `verified`).

### Автооткат

При сбое батча новые батчи не запускаются, и откатываются все хосты из `journal["previous"]` в **обратном** порядке
записи. Для хоста: если `fleet.version(host) == previous[host]` — ничего не делать; иначе при `previous[host] is None`
вызвать `fleet.remove(host)`, иначе `fleet.deploy(host, previous[host])`. Исключение `Exception` при откате хоста
не прерывает откат остальных: хост попадает в `stuck`, запись о нём остаётся в журнале. Успешно откаченные хосты
удаляются из `previous`; если не осталось ни одного `stuck`, `journal["verified"]` очищается (журнал снова пустой,
`target` сохраняется).

### Результат

```python
{
  "status": "ok" | "rolled_back" | "rollback_failed",
  "target": str,
  "batches": [[...], ...],     # результат plan_batches
  "deployed": [host, ...],     # хосты, для которых deploy(target) в ЭТОМ вызове завершился успешно, по порядку
  "rolled_back": [host, ...],  # успешно откаченные хосты, в порядке отката
  "stuck": [host, ...],        # хосты, которые откатить не удалось, в порядке отката
  "failed_batch": int | None,  # индекс батча со сбоем
  "failed_host": str | None,
  "reason": "deploy_error" | "unhealthy" | None,
  "elapsed": число,            # clock.now() в конце минус в начале
}
```

`status`: `ok` — все батчи приняты; `rolled_back` — сбой и все откаты успешны; `rollback_failed` — сбой и есть `stuck`.

### Повторный вызов

С тем же журналом `rollout` безопасен: после успешной выкатки повтор не делает ни одного вызова `fleet`/`clock`
(`deployed == []`, `elapsed == 0`, статус `ok`); после обрыва (исключение вне `Exception`) повтор продолжает с того
же места — хосты на целевой версии не выкатываются заново, а откат при последующем сбое возвращает версии, что
были **до первого** запуска (потому что `previous` не перезаписывается). После `rolled_back` журнал пуст, повтор
начинает выкатку заново.

## `DESIGN.md` (в корне репозитория)

Разделы `## Решения`, `## Компромиссы`, `## Границы применимости` — в каждом не меньше 200 символов: почему
журнал пишется до вызова `deploy`, что даёт обратный порядок отката и где он опасен (миграции схемы, несовместимые
версии), чем «здоров N раз подряд» лучше одной проверки, что произойдёт при двух параллельных оркестраторах на
один парк и как это можно было бы закрыть (блокировка, версия журнала), как бы это выглядело в Kubernetes
(`maxSurge`/`maxUnavailable`, readinessProbe) и чего оркестратор не умеет (канареечный анализ метрик).
