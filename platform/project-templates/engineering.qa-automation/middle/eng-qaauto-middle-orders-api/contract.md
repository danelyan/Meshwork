# Контракт: проверка HTTP API заказов по контракту (engineering.qa-automation, middle)

Задача QA-инженера: по описанию API написать **автоматическую проверку**, которая отличает сервис, соблюдающий контракт,
от сервисов, его нарушающих. Сам сервис писать не нужно – платформа подставляет свои реализации (Express 5).

## Что сдать

Модуль `src/verify.ts` (ES-модуль) экспортирует `verify(createApp: CreateApp): Promise<void>`. Типы – в `src/types.ts`.
`createApp()` возвращает **новое** Express-приложение с пустым состоянием (его удобно передавать в `supertest`).
`verify` вызывает `createApp` сколько нужно, проверяет поведение и **бросает `Error`** при нарушении контракта.
На соответствующем контракту сервисе `verify` ничего не бросает. Используйте `supertest`; сеть и порты не нужны.

## Контракт API

Все тела запросов и ответов – JSON. Ошибки – `{ "error": "<код>" }` (для ошибок валидации ещё `"field"`).

**`POST /orders`** – тело `{ sku: string, qty: number }`.
- `sku` – непустая строка; `qty` – целое от 1 до 10 включительно. Проверка в порядке `sku`, затем `qty`.
  Нарушение: `400 { error: "validation", field: "sku" | "qty" }`.
- Тело, не являющееся корректным JSON: `400 { error: "invalid_json" }`.
- Успех: `201` и `{ id, sku, qty, status: "new" }`, `id` – непустая строка, уникальная в рамках приложения.
- Заголовок `Idempotency-Key` (необязательный). Повтор запроса с тем же ключом и тем же телом (`sku` и `qty`) не создаёт
  заказ: ответ `200` с тем же заказом. Тот же ключ с другим телом: `409 { error: "idempotency_conflict" }`.
  Запрос, не прошедший валидацию, ключ не запоминает.

**`GET /orders/:id`** – `200` с заказом либо `404 { error: "not_found" }`.

**`GET /orders`** – параметры запроса `status` (`new | paid | cancelled`), `limit` (целое 1–50, по умолчанию 10),
`offset` (целое `>= 0`, по умолчанию 0). Ответ `200 { items: Order[], total: number }`: заказы в порядке создания,
`total` – число заказов, подходящих под `status`, **до** применения `limit`/`offset`.
Неверный параметр: `400 { error: "validation", field: "status" | "limit" | "offset" }`.

**`POST /orders/:id/pay`** и **`POST /orders/:id/cancel`** – тела не нужно. Из статуса `new` переводят заказ в `paid`
и `cancelled` соответственно (`200` и заказ). Из любого другого статуса: `409 { error: "invalid_state" }`,
заказ не меняется. Неизвестный `id`: `404 { error: "not_found" }`.

Состояние приложений независимо: заказы, созданные через одно `createApp()`, не видны в другом.

## Как оценивается

- `verify` проходит на эталонном сервисе и на независимо написанном сервисе с тем же поведением (не завязывайте
  ожидания на детали одной реализации: порядок ключей JSON, формат `id`, заголовки).
- Для каждого из набора сервисов-мутантов (нарушены коды ответов, границы валидации, идемпотентность, переходы
  состояний, пагинация, изоляция состояния и т. п.) `verify` обязан бросить. Чем больше мутантов поймано, тем выше балл.
  Видимые тесты показывают эталон и два мутанта.
- Проверка должна быть самодостаточной: не полагайтесь на порядок запусков, не используйте общее состояние между вызовами `verify`.

## Окружение проверки

Node.js 20, TypeScript без проверки типов (vitest), `express` и `supertest` предустановлены, остальные зависимости не
устанавливаются. Один вызов `verify` должен укладываться в несколько секунд (таймаут теста – 10 секунд).
