# Дашборд: проектные решения

## Решения
Все запросы идут через общий кэш по ключу. Запрос в полёте переиспользуется всеми, кто спросил тот же ключ, поэтому три виджета
на двух ключах дают два запроса. Каждая запись хранит номер поколения: «Обновить всё» объявляет запрос в полёте устаревшим, следующий
fetch начинает новый, а ответ прежнего поколения в снимок не попадает, даже если пришёл позже. Виджет подписан только на свой ключ
через useSyncExternalStore и мемоизирован с примитивными пропсами, поэтому чужие данные и состояние Dashboard его не перерисовывают.

## Компромиссы
Срок жизни фиксированный и общий для всех ключей: просто и предсказуемо, но редко меняющиеся и быстро меняющиеся данные живут одинаково.
Структурное разделение через JSON.stringify дёшево на малых ответах и ломается на больших объектах и циклических данных; взамен
повторное обновление тех же цифр не вызывает ни одного коммита. Старые данные показываются, пока идёт обновление: экран не мигает
«Загрузкой», но пользователь может увидеть устаревшую цифру. Ошибка не кэшируется — зато при падении API каждый монтаж снова бьёт в сеть.

## Границы применимости
Подход рассчитан на десятки виджетов и ответы в единицы килобайт на одной вкладке. Если ключей станут сотни, нужны вытеснение записей
и ограничение памяти; при зависимых запросах, пагинации, оптимистичных мутациях и фоновом обновлении по фокусу окна разумнее взять
готовую библиотеку запросов. Кэш живёт в памяти вкладки и не разделяется между пользователями: на общем устройстве его нужно сбрасывать
при смене учётной записи. Для живых данных опрос лучше заменить серверным пушем.
